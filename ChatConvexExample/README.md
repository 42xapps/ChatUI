# ChatConvexExample

A single-chat app built on the `ExyteChat` package, backed by **Convex**
(history + realtime), **Clerk** (auth), and **Cloudflare R2** (attachments).

One conversation per user. **No groups, no human-to-human chat** — the app opens
straight into the signed-in user's thread, the way
`ChatExample/ContentView.swift` opens straight into `ChatExampleView`. The other
party will be an LLM; that isn't built yet.

`ChatFirestoreExample/` is left untouched as the reference.

## Running it

1. Deploy the backend — see [`../convex-backend/README.md`](../convex-backend/README.md).
   `npx convex dev` must be running (or `convex deploy`), with
   `CLERK_FRONTEND_API_URL` and the four `R2_*` variables set on the deployment.
2. In the Clerk Dashboard:
   - Activate the **Convex integration** (`dashboard.clerk.com` → Convex). This
     maps the `aud: convex` claim onto the default session token, which is what
     `auth.config.ts` matches. There is no separate `convex` JWT template to
     create for the Swift SDK.
   - Enable the sign-in methods you want under **Email, phone, username**.
     `AuthView` renders whatever is enabled there — the app configures none of
     it in code.
3. Fill in `ChatConvexExample/Config.xcconfig`.
4. Open `ChatConvexExample.xcodeproj` and run.

`Config.xcconfig` holds only client-public values (Clerk publishable key, Convex
deployment host). R2 credentials live on the Convex deployment and never reach
the app.

## Regenerating the project

The project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen)
from `project.yml`. The generated `.xcodeproj` is committed, so XcodeGen is only
needed when the file list changes:

```sh
cd ChatConvexExample && xcodegen generate
```

## How it maps to the Firestore version

| Firestore version | Here |
| --- | --- |
| `AuthViewModel` + `AuthView` (device id + nickname) | Deleted. Clerk's prebuilt `AuthView(isDismissible: false)` is the signed-out root. |
| `SessionManager` (device-id lookup) | Same caching shape; identity comes from the Clerk session, projected into a Convex `users` row by `users.syncCurrentUser`. |
| `DataStorageManager` (two snapshot listeners) | Deleted with the conversation list. The one remaining subscription lives in `ConversationViewModel`. |
| `ConversationsView` / `UsersView` / group screens | Deleted — no list, no directory, no groups. |
| `ConversationViewModel.subscribeToMessages` | Subscription to `messages:listForConversation`. The optimistic-insert-then-reconcile-by-id logic is unchanged. |
| `bumpUnreadCounters()` / `resetUnreadCounter()` | Deleted. With a single always-on-screen chat, "unread" has no meaning. |
| `UploadingManager` (Firebase Storage) | Presigned R2 PUT: `attachments:requestUploadUrl` → `URLSession.upload` straight to R2. Returns object keys, not URLs. |
| `FirestoreMessage` / `FirestoreConversation` | `Convex*` DTOs in `Convex/ConvexDTO.swift`, each naming the validator it mirrors. |
| `FakeConversationsManager` | Deleted — it fabricated client-side users, which is what Clerk replaces. |
| `.whereField("users", arrayContains: uid)` | The `conversationMembers` join table, indexed by user, checked server-side before any read or write. |

## Things worth knowing

**Message identity is a client-generated `clientId`, not Convex's `_id`.**
Firestore let the client choose a document id, which is the basis of "insert
locally as `.sending`, replace when the server copy arrives with the same id".
Convex assigns `_id` server-side, so messages carry a `clientId` the sender
mints up front. It's indexed, which also makes `messages.send` idempotent under
retry.

**Attachments store R2 keys, not URLs.** The backend derives a URL on read, and
the client uses the keys as image-cache keys — so caching survives a change of
URL scheme, and a live subscription re-delivering a message doesn't invalidate
the cache.

**The root gates on the Convex `users` row, not just on auth.** Every backend
function calls `requireCurrentUser`, so `ChatHomeView` is not constructed
until `users.syncCurrentUser` has landed. Without that gate,
`conversations:listMine`/`conversations:create` race the sync and throw.

**Swift 5 language mode.** Matches `ChatFirestoreExample`'s target and
`ExyteChat`'s own `swiftLanguageModes: [.v5]`. The ported view model mutates
`@Published` state from a Combine callback under an `NSRecursiveLock`, which
Swift 6 strict concurrency would reject.

## Out of scope

No LLM integration, no voice-to-voice, no mem0 — and no stubs for them. The
terminal action is "send a message".
